RTL8139 网络驱动
================

``drivers/net/rtl8139/`` 为 Ethernet PCI ``10ec:8139`` 提供原生 RTL8139
驱动。``CONFIG_RTL8139`` 为 tristate，默认内置；设置为 ``m`` 时生成
``drivers/net/rtl8139/rtl8139.ko``，携带对应的 PCI 模块别名。每个匹配
的 PCI 功能独立注册网络接口，复用现有 IPv4/IPv6、socket 和网络配置接口。

设备范围与收发
==============

驱动使用经典 RTL8139 的 I/O BAR0、32 位 DMA 地址和内置 PHY 状态，
包括 QEMU 的 RTL8139C+ 模型在经典模式下的使用。它与 ``r8169`` 的
RTL8168/RTL8125 驱动独立，不启用 C+ 描述符模式或硬件校验和卸载。
仅提供 MMIO、没有有效 256 字节 I/O 窗口的设备返回不支持。

接口 MTU 为 1500。发送支持四个独立的 2048 字节缓冲区；短帧补零至
60 字节，由硬件添加 FCS。队列满返回 ``EAGAIN``，不等待硬件完成。
仅在设备交回所有权并报告终态后才复用发送缓冲区。

接收使用带额外 DMA 安全空间的 32 KiB 环，处理跨环边界的报文、
四字节记录对齐和 CAPR 的 16 字节偏移。驱动校验状态与长度，剥离 FCS；
CRC 等错误和输出容量不足的记录被消费并报告错误，不阻塞后续报文。
接收过滤允许本站单播、广播和多播，以支持 IPv6 邻居发现。

RTL8139 使用传统 INTx。驱动保持设备中断屏蔽和 PCI INTx 禁用，使用
现有任务上下文轮询，不猜测共享 IRQ 路由。其吞吐量和 CPU 开销需要
单独实测，不能从标称 100 Mbit/s 推断实际性能。

资源与恢复
==========

PCI 能力链经过长度、对齐和循环检查后才能请求 D0。RX/TX 缓冲区由
DMA32 分配器分配，并验证完整地址范围和 CPU 映射；物理地址不会作为
CPU 指针使用。全部缓冲区就绪后才启用 PCI bus master 和收发引擎。

接收溢出、损坏的记录长度或五秒未完成的发送触发有界控制器复位，
在确认停止后重建已有队列；在途报文可能丢失，由上层协议处理。
恢复不分配内存或睡眠。复位失败或 PCI 总线错误使设备停止接收新请求，
保留 DMA，等待卸载或重新加载时的安全处理。

卸载先关闭并排空网络回调，再禁用 bus master、屏蔽设备中断并确认复位。
无法证明停止时向管理器报告错误，保留设备、DMA 和模块代码供后续重试。
释放缓冲区后不恢复固件原先启用的 bus master 位。

使用与验证
==========

在 ReliefOS 父仓中，可以选择该 QEMU 设备：

.. code-block:: sh

   make run QEMU_NETWORK=rtl8139
   # 宿主没有 KVM 时追加 QEMU_KVM=0。

``tools/test_rtl8139.py`` 在 ASan/UBSan 下编译真实驱动对象，只替换
PCI、端口 I/O、DMA 和核心服务边界。它覆盖设备匹配、D0、DMA32、
收发回绕、补零、背压、错误记录、溢出与超时恢复、多设备隔离以及
初始化回滚和失败 STOP 的资源保留。

内核的 ``tools/tests/multinic_guest.c`` 提供标准 socket 探针；其
``stress`` 模式逐地址族校验 1 MiB TCP 回显数据和 32 个不同长度的 UDP
数据报。ReliefOS 的 ``tools/test_rtl8139_qemu.py`` 编排两张 RTL8139 与
一张 e1000e，检查独立 DHCP、IPv4/IPv6、并发数据、carrier 断开恢复，
以及模块卸载期间其他驱动的活动连接和重新加载。

宿主边界测试、QEMU BIOS/UEFI、模块重载和实体硬件验证分别记录结果。
QEMU 的成功不表示实体 RTL8139 或 VMware 已经验证。

寄存器语义参照 `QEMU RTL8139 设备模型
<https://github.com/qemu/qemu/blob/v7.2.0/hw/net/rtl8139.c>`_ 核对。
实现为 ReliefNT 原创 Apache-2.0 代码，不包含该 GPL 源文件的实现代码。
